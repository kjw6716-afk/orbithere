# 커뮤니티 운영 보완

## 현재 적용 범위

제목형 게시판은 SQL 011·작성 제한 보완과 `20260911213759_titled_community_board.sql`이 필요합니다.
별도 유료 번역 API는 사용하지 않습니다. 사진은 Supabase Storage의 저장·전송 사용량에 포함됩니다. 신고/옛 글 삭제 요청은 기존 reports와
관리자의 report_queue/resolve_report를 사용합니다. 신고자와 일반 이용자는 접수함을 읽을 수 없습니다.

GitHub Pages에 병합하는 것만으로 SQL은 실행되지 않습니다.
`supabase/migrations/20260911204442_community_readiness_hardening.sql`은 **2026-09-12 운영 적용을 완료했습니다.**
처음 적용 요청은 자동 승인 검토에서 보류됐지만, 이후 사용자가 이 운영 DB 변경을 명시적으로 승인했습니다.
Supabase 마이그레이션 버전은 `20260911210425`, 이름은 `community_readiness_hardening`입니다.
저장소 파일명의 생성 시각과 서버의 실제 적용 버전은 서로 다릅니다.
적용 후 보안 버전 2, 기존 콘텐츠 내용 지문 보존, 새 트리거·권한·인덱스를 확인했습니다.
적용 전 함수 정의와 실행 권한을 조회해 복구 경로를 확인했습니다. 이 확인은 전체 DB 백업 또는 복원 시험을 대신하지 않습니다.

## 검토할 SQL의 범위

- `orbit_private.write_events`: 작성자 ID·대상 ID·종류·시각만 기록. 본문·닉네임·IP는 복사하지 않습니다.
  공개/인증 API 역할 모두 스키마·테이블 접근 권한이 없고 RLS를 활성화합니다.
- posts는 분당 3건/시간당 20건, comments는 5건/50건, reports는 5건/30건으로 기존 수치를 유지합니다.
  실제 게시물 삭제와 별개로 성공한 쓰기를 세며 작성자·종류별 트랜잭션 잠금을 사용합니다.
- 1시간이 지난 기록은 다음 정상 글·댓글·신고 저장 시 삭제됩니다. 정기 작업은 설치하지 않습니다.
  계정이 삭제되면 연결된 제한 기록도 삭제됩니다. 기존 콘텐츠는 변경하거나 삭제하지 않습니다.
- 관리 RPC의 비인증 호출 권한과 트리거 전용 함수의 직접 호출 권한을 회수합니다.
  관리자 여부를 확인하는 기존 함수 내부 검증은 유지됩니다.
- 글 전체/채널별, 댓글 스레드의 `(created_at,id)` 탐색 인덱스를 추가합니다.
- 한 트랜잭션으로 실행하며 잠금 획득 제한은 5초입니다. 실패 시 일부만 적용되지 않습니다.

검증: 실제 마이그레이션을 PGlite에서 두 번 실행하고 소유권, 관리자 접근, 비공개 신고,
글/댓글 삭제 후 재작성, 대량 INSERT 롤백, 시간당 제한과 만료 기록 정리를 확인합니다.
PGlite는 단일 연결이므로 병렬 부하 시험을 수행했다고 간주하지 않습니다.

## 재적용·복원 시 참고

1. 대상이 기존 Orbit 프로젝트인지 확인하고 최신 복구 수단/백업 상태를 점검합니다.
   신규 DB에서는 루트의 schema.sql, 002…011을 먼저 적용하고 이 timestamp 마이그레이션을 실행합니다.
   기존 프로젝트에 초기 스키마를 다시 실행하지 않습니다. 레거시 SQL은 CLI migrations 폴더로 자동 이관되지 않습니다.
2. 개인정보처리방침의 아래 제한 기록 안내가 실제 운영과 일치하는지 확인합니다.
3. Supabase 마이그레이션 기능 또는 SQL Editor로 검토한 SQL 전체를 한 번 적용합니다.
4. 새 테이블 접근 차단, 관리자 RPC 권한, 세 종류의 INSERT 트리거, 탐색 인덱스,
   공개 조회와 기존 콘텐츠 보존을 확인합니다. 운영 게시물은 자동 테스트 재료로 생성/삭제하지 않습니다.
5. 처리 결과·적용 시각·마이그레이션 버전을 PROJECT_STATUS에 기록합니다.

개인정보처리방침에 반영한 안내:

> 삭제 후 반복 작성하는 도배를 막기 위해 글·댓글·신고의 작성자 ID, 대상 ID, 종류, 작성 시각을
> 비공개 제한 기록에 보관합니다. 이 기록에는 본문·닉네임·IP 주소를 추가로 저장하지 않습니다.
> 게시물을 지워도 제한 기록은 즉시 삭제되지 않습니다. 작성한 지 1시간이 지나면 다음
> 글·댓글·신고가 정상 저장될 때 함께 삭제되며, 해당 인증 계정 삭제 시에도 제거됩니다.

문제가 발생하면 새 트리거만 제거하고 기존 posts_rate_limit/comments_rate_limit/reports_rate_limit
트리거를 복구하는 별도 검토된 수정으로 대응합니다. 원인 조사 전 기록 테이블이나 콘텐츠를 지우지 않습니다.
기존 함수는 남겨 두므로 트리거 복구에 함수 재작성은 필요 없습니다.

## 운영자가 계속 확인할 것

새 익명 계정을 만드는 공격까지 작성자별 제한으로 막을 수는 없습니다.
Supabase의 가입 제한과 CAPTCHA 설정은 실제 서비스 키 및 가입 흐름 검증 후 별도로 적용합니다.
인증 세션 초기화와 닉네임 중복은 현재 제한입니다. 사진 정리는 아래 절차를 따릅니다.

관리자는 신고함을 정기적으로 확인하고 삭제 요청의 대상과 권한을 검토합니다.
공개 게시판에 비밀번호·인증 코드·신분증을 요구하지 않습니다. 신고 외 일반 비공개 연락 경로는 아직 없습니다.

## 제목형 게시판과 사진

- 제목 1~80자, 내용 1~5,000자, 댓글 1~300자. 기존 내용·ID는 유지하고 기존 글 첫 줄에서 제목을 생성합니다.
- 관리자만 공지를 고정·해제할 수 있으며 최대 3개입니다. 글 상세의 ‘공지로 고정’ 또는 글쓰기의 공지 체크박스를 사용합니다.
- `board_posts`는 본문을 내려주지 않는 목록 API입니다. 상세 URL은 기존 `lounge.html?post=UUID`를 유지합니다. 댓글·공감은 상세에서만 읽습니다.
- 주기적인 타임라인 폴링은 없습니다. 목록/댓글 새로고침과 커서 기반 이전 항목 조회를 사용합니다.
- 사진은 JPG/PNG/WebP, 원본 한 장 15MB·4,000만 화소 이하, 글당 5장입니다. 일반 UI는 EXIF 없이 JPEG로 재인코딩하고 긴 변 2,048px·2MB 이하, 별도 200px 썸네일을 만듭니다. 사진 속 개인정보는 자동 마스킹하지 않습니다.
- `board-images`는 비공개 버킷입니다. 게시 전에는 작성자/관리자만, 게시 후에는 공개 SELECT 정책을 통해 다운로드할 수 있습니다. 덮어쓰기와 다른 사람의 예약 경로 업로드는 금지됩니다.
- `reserve_board_images`가 인증 작성자의 고유 경로를 예약합니다. 한 시간에 최대 20장이고 삭제해도 제한이 초기화되지 않습니다. 예약은 1시간 유효하며 오래된 기록은 다음 예약 시 정리합니다.
- 게시 RPC는 원본과 썸네일의 존재·예약 소유권을 확인한 뒤 사진을 연결합니다. 글 생성 UUID를 유지해 응답 유실 후 같은 요청을 재시도해도 중복 게시되지 않습니다.
- 삭제 시 DB 글을 먼저 지워 일반 공개 다운로드 권한을 회수한 뒤 Storage API로 파일을 삭제합니다. 이미 내려받은 사본이나 발급된 다운로드 링크의 캐시까지 회수한다고 보장하지 않습니다.
- 업로드 중단/파일 삭제 실패 시 비공개 파일이 남을 수 있습니다. 관제실의 ‘게시판 사진 정리’는 하루 이상 된 미연결 파일을 한 번에 최대 100개씩 지웁니다. 게시 중인 파일은 DB 정책이 삭제를 차단합니다. 자동 파일 정리 작업은 설치하지 않습니다.
- Storage 파일은 반드시 Storage API로 삭제합니다. SQL로 `storage.objects`만 지우면 실제 저장된 파일은 정리되지 않습니다.

배포 전에 보드 마이그레이션을 적용하고 `board_version()=1`, `community_version()=2`를 확인합니다.
운영에는 `20260911221455_titled_community_board`로 2026-09-12 07:14 KST에 적용했습니다.
기존 내용 지문·개수 보존과 버킷 정책을 확인했으며 상세 기록은 PROJECT_STATUS에 있습니다. UI 롤백이 필요해도 새 제목·사진 연결 컬럼이나 버킷을 삭제하지 않습니다.
이전 UI의 짧은 글 작성은 새 서버에서도 호환되지만, 새 기능에는 새 UI가 필요합니다.

## 공식 뉴스

`news.html`은 `data/news.json`의 공식 제목과 링크를 표시합니다. `scripts/update_news.py`가 기관·기업 출처별 최근 8건,
총 최대 64건을 가져옵니다. 기사 본문·보도 사진·자동 번역 전문을 재게시하지 않습니다.

- 한국천문연구원: https://www.kasi.re.kr/rss/newsMaterial
- NASA / JPL: https://www.nasa.gov/centers-and-facilities/jpl/feed/
- ESA 우주과학: https://www.esa.int/rssfeed/Our_Activities/Space_Science

기관의 공식 RSS 안내에서 확인한 주소입니다. JPL의 별도 jpl.nasa.gov 피드는 실행 환경에서 403을 반환해,
NASA 본사이트가 제공하는 JPL 피드를 사용합니다. 외부 URL·미래 날짜·XML 엔티티·과대 응답을 검증합니다.
영문 기사는 원제 펼쳐보기·원문 읽기를 제공하며, 별도 `data/news-summaries.json`에 원문 대조를 마친 한국어 핵심 요약이 있으면 함께 표시합니다. Google 웹사이트 번역 링크는 제거했습니다. 번역 API 키는 없습니다.

GitHub Actions ‘공식 우주 뉴스 갱신’이 2시간마다 실행됩니다. 스케줄은 GitHub 사정으로 지연될 수 있습니다.
수집 실패 출처는 이전 목록과 정상 확인 시각을 유지하며 화면에 상태를 표시합니다. 모든 수집이 실패해도
기존 뉴스는 지우지 않습니다. 마지막 정상 확인이 48시간을 넘으면 지연 안내를 표시합니다.

토큰으로 만든 커밋은 Pages 빌드를 자동 촉발하지 않으므로 워크플로가 Pages의 공식 빌드 API를 명시적으로 요청합니다.
실패한 워크플로는 Actions에서 확인·재실행합니다. 이 작업은 main에 뉴스 데이터만 커밋하며 강제 푸시는 하지 않습니다.
본문 검색은 현 규모에서 부분 문자열 검색을 사용합니다. 데이터 증가 시 실행 계획과 전문 검색 도입을 검토하세요.

## 게시글 조회수 (2026-09-13)

- `post_view_counts`는 글별 누적 숫자만 공개합니다. 목록·공지·상세에 표시하며 기존 글은 적용 후 0부터 시작합니다. 글 자체의 내용·작성 시각은 바꾸지 않습니다.
- 실제 상세 내용을 불러온 뒤 `record_post_view`를 호출합니다. 목록·검색·미리보기는 세지 않습니다. 기존 Supabase 인증을 사용하며 계정이 없으면 닉네임 입력 없이 익명 인증을 준비합니다.
- 같은 인증 계정/글은 30분에 한 번 집계합니다. 서버의 유일 키와 조건부 UPSERT가 재시도·동시 중복 요청을 막고 숫자는 원자적으로 증가합니다. 새 브라우저·계정 생성까지 막는 절대적 방문자 수는 아닙니다.
- `orbit_view_private.recent_views`에는 계정 ID·글 ID·마지막 집계 시각만 보관합니다. API 역할은 직접 읽거나 쓸 수 없습니다. 30분이 지난 기록은 정상 조회 요청 끝에서 오래된 순으로 최대 500건씩 잠긴 행을 건너뛰며 정리합니다. 글/계정 삭제 시 연결 기록을 지우며, 글 삭제 시 누적값도 지웁니다.
- 공개 RPC는 SECURITY INVOKER, 비공개 함수는 인증 확인·고정 search_path·명시적 EXECUTE 권한을 사용합니다. 누적값 테이블은 공개 읽기만 허용하며 임의 INSERT/UPDATE/DELETE/TRUNCATE를 허용하지 않습니다.
- 상세의 숫자 읽기·집계 오류는 본문 읽기를 막지 않습니다. 마지막으로 확인한 숫자를 유지하고, 한 번도 읽지 못한 값은 `조회 —`로 표시합니다.
- `view_count DESC, post_id` 인덱스를 준비했습니다. 인기글 탭이나 인기순 정렬 UI는 이후 별도 작업입니다.
- 운영 적용은 `20260913095912_post_view_counts.sql` 검증 후 진행합니다. Pages 병합만으로 SQL이 실행되지 않습니다. 롤백은 이전 UI로 복귀하고 누적값·조회 기록은 보존하는 방식이며, 기존 board_posts 필드와 매개변수는 유지됩니다.

## 홈 이야기 순서

`story-carousel.js`가 매 페이지 로드 때 전체 공개 이야기 순서를 한 번 섞습니다. 현재 탭의 직전 시작 이야기 주소 하나를 sessionStorage에 기억해 같은 이야기의 연속 시작을 피합니다. 저장이 막히면 무작위 순서만 적용합니다. 크기 변경·동작 줄이기 전환에서는 다시 섞지 않으며, 복제 카드는 섞인 원본과 같은 순서를 따릅니다. JavaScript가 꺼져 있으면 기존 정적 발행 순서를 읽습니다.
